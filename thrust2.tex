\subsection{Thrust 2: Scalable Runtime Trust Attestation.}
\label{sb:t2}

\textbf{Problem Statement.}
Establishing a trusted execution domain does not guarantee that the software within that domain continues to execute as intended.
Secure boot and conventional remote attestation can establish properties of the loaded software or initial system state, but they do not capture how the software behaves after execution begins.
An attacker who exploits a runtime vulnerability may therefore redirect control flow, manipulate task execution, or abuse asynchronous system events without changing the initially attested binary.
Control-flow attestation (CFA) addresses part of this problem by allowing a remote verifier to reason about the execution path taken by a program.
However, existing CFA approaches are difficult to apply to realistic embedded systems because their evidence or measurement cost may grow with execution duration or program complexity, while protected-domain transitions and cryptographic operations can introduce significant runtime overhead.

Embedded execution also differs fundamentally from the simple single-threaded program model assumed by many attestation schemes. Bare-metal firmware and RTOS
systems are event-driven and may include interrupts, exception handlers, callbacks, task scheduling, context switches, and interactions among privileged and unprivileged components.
These events alter the authorized execution state and can interleave with application control flow, making a conventional single-program trace insufficient to represent what actually occurred.
Furthermore, the measurement state itself must remain protected while these asynchronous transitions take place.

This thrust therefore asks the following fundamental question:
\textbf{\textit{How can resource-constrained embedded systems generate compact and protected runtime evidence that enables a remote verifier to reason about authorized execution across long-running, interrupt-driven, and multitasking workloads without evidence growing with execution duration?}}
Addressing this question requires new representations of embedded execution, hardware-assisted measurement mechanisms, and verifier algorithms that capture
control-flow, task, interrupt, and other security-relevant events while bounding runtime, memory, and communication overhead.


\textbf{Related Work.}
Prior work on remote attestation has progressed from static software-integrity verification to runtime control-flow attestation.
Pioneer~\cite{seshadri2005pioneer}, VIPER~\cite{li2011viper}, PUFatt~\cite{kong2014pufatt}, and related hardware-assisted schemes~\cite{armknecht2013security,eldefrawy2012smart} establish code integrity or trustworthy execution state, but do not capture runtime control-flow hijacking.
Control-flow attestation (CFA) addresses this limitation by reporting execution behavior.
C-FLAT, OAT, Blast, DIAT~\cite{abera2019diat}, ARI~\cite{wangari}, ReCFA~\cite{zhang2021recfa}, SpecCFA~\cite{caulfield2024speccfa}, and ScaRR~\cite{toffalini2019scarr} explore different tradeoffs in trace granularity, evidence size, and verifier complexity, while CFA+~\cite{299850} combines local control-flow enforcement with lightweight attestation.
Specialized-hardware approaches, including VRASED~\cite{nunes2019vrased}, ACFA~\cite{caulfield2023acfa}, LiteHAX~\cite{dessouky2018litehax}, Tiny-CFA~\cite{nunes2021tiny}, LO-FAT~\cite{dessouky2017fat}, and IDA~\cite{arkannezhadida}, provide stronger monitoring capabilities but often rely on dedicated or modified hardware.
Despite these advances, existing approaches remain limited in supporting long-running, interrupt-driven, and multitasking embedded execution while simultaneously bounding evidence size, runtime overhead, and verifier complexity.
Thrust~2 addresses this gap by developing scalable runtime evidence and verification mechanisms for realistic bare-metal and RTOS-based embedded systems.


\textbf{Task 2.1: Compact and Verifier-Efficient Runtime Evidence}
We will investigate runtime attestation mechanisms that keep both transmitted evidence and verifier cost practical as embedded applications become larger and execute for longer periods.
Rather than recording complete execution traces whose size grows with the number of executed control-flow transfers, we will develop compact execution representations whose size is primarily determined by program structure.
A central objective is to jointly optimize prover-side evidence generation and verifier-side reconstruction so that reducing communication overhead does not simply transfer excessive complexity to the remote verifier.

As preliminary work, we developed \enola~\cite{armanuzzaman2026enola}, which demonstrates that scalable control-flow evidence can be generated on commodity embedded processors without modifying the processor architecture.
As illustrated in Figure~\ref{fig:enola}, the verifier first issues a fresh challenge, after which the trusted \enola attestation engine initializes the measurement keys and protection mechanisms.
During program execution, compiler-inserted instrumentation records a basic-block occurrence trace while Arm Pointer Authentication instructions incrementally compute separate measurements for forward and backward control-flow transfers.
The occurrence trace is maintained in TrustZone-protected memory, whereas the forward and backward measurements are retained in compiler-reserved registers so that they are not exposed to ordinary program memory.
At the end of execution, these components are combined with the verifier challenge into an authenticated report and transmitted to the verifier, which reconstructs candidate execution paths and validates them against the received measurements.
This design makes the transmitted authenticator linear in the number of program basic blocks rather than the length of the executed path and substantially reduces communication cost; for example, \enola requires an average of 397 bytes for Embench compared with 21,009 bytes for Blast. 


Although \enola significantly reduces transmitted evidence, this compression exposes a new scalability challenge at the verifier.
Different execution paths can sometimes produce the same basic-block occurrence information, requiring the verifier to explore multiple candidate paths before finding one consistent with the received measurements.
This ambiguity can cause verification cost to grow rapidly for programs with increasingly complex control-flow structures.

Building on this observation, we will develop ambiguity-aware runtime evidence that introduces additional information only for portions of the control-flow graph where the compact representation is insufficient to uniquely characterize execution.
We will design static analyses to identify such ambiguous regions, determine what additional runtime information is necessary to distinguish their feasible paths, and generate this information selectively rather than increasing evidence for the entire program.
We will correspondingly develop verifier algorithms that use these localized hints to prune infeasible paths early and bound reconstruction effort around the ambiguous regions.
For continuously executing firmware, we will further investigate checkpointed and epoch-based attestation that periodically finalizes and authenticates bounded execution intervals, allowing runtime verification to continue indefinitely without requiring program termination or evidence growth proportional to total execution time.

\textbf{Task 2.2: Attestation of Interrupt-Driven and Multitasking Execution}
We will investigate how runtime attestation can be extended from a single attested program to realistic embedded execution involving interrupts, RTOS tasks, scheduler activity, and context switches.
In these systems, execution frequently moves among application tasks, interrupt service routines (ISRs), and privileged scheduler code.
These transitions are legitimate, but they are not naturally represented by a single application control-flow graph and can interrupt, suspend, or resume different execution contexts.
As a result, attesting only the main application does not provide the verifier with sufficient evidence to determine whether asynchronous and multitasking execution remained authorized.

Our preliminary work, \enola~\cite{armanuzzaman2026enola} uses an ISC-FLAT-inspired secure ISR dispatcher to preserve control-flow attestation in the presence of untrusted interrupts~\cite{neto2023isc}.
The dispatcher intercepts interrupts through the TrustZone-protected NVIC, securely saves the interrupted program context and measurement state, protects the program stack during ISR execution, and restores the context on return.
This protects the attested program from malicious ISRs, but the ISR execution itself is not included in the control-flow evidence.
Therefore, the verifier can confirm safe resumption of the attested program, but cannot verify whether the ISR followed an authorized execution path.

We will extend this foundation by treating interrupt handlers, RTOS tasks, and scheduler execution as first-class attested execution contexts.
Each context will be associated with its own control-flow representation and protected measurement state, while interrupt entry, interrupt return, task preemption, scheduler dispatch, and task context switches will be represented as authenticated transitions among these contexts.
As illustrated in Figure~\ref{fig:rtos-attestation}, when an interrupt or scheduling event changes the active execution context, the runtime will securely suspend and authenticate the current measurement state, initialize or restore the measurement state of the next context, and record the transition as part of the attestation evidence.
For interrupt-driven execution, the evidence will bind the interrupted context, interrupt source, selected ISR, ISR execution measurement, and authenticated return.
For multitasking execution, the evidence will additionally bind task identities, scheduler-mediated transitions, and the corresponding suspend and resume operations.

A central challenge is to protect multiple measurement states without introducing excessive trusted-world transitions, memory overhead, or replay opportunities.
We will investigate protected per-context measurement states that are securely stored and restored using hardware-supported cryptographic mechanisms, such as Pointer Authentication or lightweight MAC primitives, together with TrustZone-protected runtime support.
Each suspended context will be cryptographically bound to its execution identity and transition history so that a compromised task or ISR cannot substitute, replay, or reuse the measurement state of another context.
We will also investigate nested interrupts and preemptive scheduling, where multiple execution contexts may be suspended simultaneously, by maintaining an authenticated hierarchy of active and suspended measurement states.

At the verifier, we will develop a hierarchical execution model that combines task-specific, ISR-specific, and scheduler control-flow graphs with an authenticated transition graph describing asynchronous and scheduling events.
The verifier will check both \emph{intra-context execution}, determining whether each task or ISR followed an authorized control-flow path, and \emph{inter-context execution}, determining whether interrupts, scheduler decisions, context switches, and returns occurred through authorized transitions.
This will enable the verifier to establish not only that individual applications remained protected, but also that the overall interrupt-driven and multitasking execution of the embedded system remained consistent with its expected runtime behavior.ined consistent with the expected embedded-system behavior.
