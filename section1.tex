\section{Overview and Objectives}
\label{sec:overview}
% ==========================================================

Embedded systems have become fundamental components of modern computing infrastructure, supporting sensing, communication, control,
and decision-making in applications ranging from industrial automation and transportation to medical devices, smart infrastructure, and the Internet of Things (IoT).
Two ARM processor classes dominate this landscape.
Cortex-A application processors, which provide an MMU and run Linux-class software, are increasingly used in automotive cockpit and driver-assistance platforms~\cite{arm2024automotive} and in IoT and edge-AI devices such as smart cameras and factory-floor machines~\cite{arm2025a320}.
Cortex-M microcontrollers (MCUs) run bare-metal or RTOS firmware without a memory management unit (MMU) and account for three-quarters of ARM's annual chip shipments and almost half of the more than 200 billion chips it has shipped to date~\cite{arm2021chips}.
Alongside these ARM classes, reconfigurable FPGA SoCs with programmable logic have gained traction, especially in edge-acceleration settings where fixed silicon falls short.
The number of connected IoT devices alone is projected to reach 39 billion by the end of 2030~\cite{iotanalytics2025}.
Unlike traditional desktop and server systems, embedded devices often operate under tight computation, memory, energy, and timing constraints, interact directly with sensors and actuators, while remaining field deployed for years without any inspection of their software.
Consequently, compromise of an embedded device can affect not only software confidentiality and integrity, but also the physical
processes that the device monitors or controls, and it can remain undetected for as long as no operator is present to notice anomalous behavior.
Recognizing these risks, recent guidance from multiple federal agencies now requires device-level cybersecurity capabilities spanning exactly the application domains named above: NIST's IoT Core Baseline profile underlies the U.S. Cyber Trust Mark consumer-labeling program~\cite{nist2022ir8425}, the FDA's 2023 premarket cybersecurity guidance is now a statutory requirement for medical devices~\cite{fda2023cybersecurity}, and CISA's Secure-by-Design principles, joined by seventeen U.S. and international partner agencies, call for the same shift toward built-in, continuously verifiable device trustworthiness this proposal pursues~\cite{cisa2023sbd}.

These risks are not hypothetical.
In July 2025, researchers exploited Bluetooth-stack vulnerabilities to achieve remote code execution on the infotainment ECUs of vehicles from Mercedes-Benz, Volkswagen, and \v{S}koda~\cite{perfektblue2025}.
Beginning in 2023, attackers compromised programmable logic controllers (PLCs) across U.S. water and wastewater utilities using nothing more than default credentials, in one case seizing control of a Pennsylvania utility's booster station~\cite{cisa2023unitronics}.
In 2020, a single vulnerable TCP/IP library embedded in hundreds of millions of devices across the healthcare, industrial, and transportation sectors was shown to allow remote code execution through one crafted network packet~\cite{cisa2020ripple20}, and a separate set of memory-corruption vulnerabilities disclosed the same year affected FreeRTOS+TCP itself~\cite{zimperium2018freertos}.
Each incident shares a common structure: a memory-corruption or authentication flaw in one embedded software component was sufficient to compromise the physical behavior of a field-deployed, unattended device, with only a slow and costly recall or firmware push as remedy.
\textbf{Because embedded devices cannot rely on a human to notice compromise or a routine patch cycle to fix it, establishing and continuously verifying their trustworthiness, remotely and throughout deployment, is essential, not merely desirable.}

The firmware and software of these systems are commonly developed in memory-unsafe languages such as C and C++.
On Cortex-M, weak process isolation results from the absence of an MMU and only two hardware privilege levels, so the memory-corruption vulnerabilities lead to control-flow hijacking, unauthorized memory or peripheral access, and complete software compromise.
Cortex-A systems have an MMU and exception levels, which strengthen isolation among Normal-world processes.
Yet the TEEs that both classes provide through ARM TrustZone offer only a single Secure world, in which privileged secure-side software, such as the TEE OS or secure firmware and its drivers, shares one hardware protection domain, so a flaw in it can expose every trusted service and the Normal world~\cite{pinto2019demystifying,cerdeira2020sok,cerdeira2022rezone,kuhne2024aster}.
Modern embedded platforms increasingly provide improved hardware security mechanisms, including memory protection units (MPUs), hardware cryptographic engines, and architectural control-flow protection such as ARM's Pointer Authentication and Branch Target Identification extension~\cite{m85}.
On Cortex-A, ARM's Confidential Compute Architecture (CCA) further adds Granule Protection Tables (GPT) that let trusted firmware control access to physical memory per granule~\cite{li2022design}; ARM positions CCA for both cloud and edge workloads~\cite{armcca}, and it is arriving in automotive-class silicon such as Neoverse V3AE~\cite{arm2024v3ae}.
However, the presence of these mechanisms alone neither guarantees that the hardware/software composition of the system can be verified nor that its trustworthiness holds throughout later execution.

\textbf{First, existing systems provide limited ability to determine precisely what constitutes the trusted execution environment.}
Prior work has pursued more flexible trusted execution along several lines, but none makes the composition of an application-specific trusted domain remotely verifiable on off-the-shelf hardware.
vTZ~\cite{hua2017vtz}, Sanctuary~\cite{brasser2019sanctuary}, and Keystone~\cite{Keystone2020} construct multiple isolated domains by virtualizing TrustZone and partitioning memory access, but TEE and REE still time-share the hardware resources, leaving them susceptible to side-channel attacks.
RISC-V-specific or new-hardware solutions such as CURE~\cite{bahmani2021cure}, Composite Enclaves~\cite{schneider2020pie}, and HECTOR-V~\cite{nasahl2020hector} instead grant exclusive access to cores, caches, or peripherals, but are not deployable on off-the-shelf platforms.
On Cortex-A, ReZone~\cite{cerdeira2022rezone} partitions the TrustZone Secure world but relies on SoC-specific controllers, and recent CCA work isolates user-space applications~\cite{zhang2023shelter}, Realm sandboxes~\cite{kuhne2024aster}, or Realm communication~\cite{sadi2026sharing}, but none decomposes the Secure world or makes the resources that compose a domain verifiable.
Reconfigurable hardware~\cite{armanuzzaman2024building} and, on Cortex-A, CCA's granule protection suggest ways out, but a fundamental question remains: \emph{\ul{how can an embedded system construct an application-specific trusted execution environment whose hardware and software composition can itself be verified by a remote party?}}

\textbf{Second, establishing a trusted environment does not guarantee that its software continues to execute as intended.}
A correctly loaded program can later be compromised through a runtime attack (e.g., ROP, JOP, Data-only) that secure boot and conventional attestation cannot see.
Control-flow attestation narrows this gap: C-FLAT~\cite{abera2016c}, OAT~\cite{sun2020oat}, ARI~\cite{wangari}, and whole-program path attestation~\cite{yadav2023whole} allow a remote verifier to reason about the execution path a program took, but their evidence or measurement cost still grows with execution duration or program complexity, and none adequately represents the interrupts, task transitions, and context switches of realistic bare-metal and RTOS execution rather than a single-program trace.
Thus, a second fundamental question is: \emph{\ul{how can embedded systems provide scalable and protected runtime evidence that enables a verifier to detect runtime violations across bare-metal and multitasking environments without evidence growing with execution duration?}}

\textbf{Third, existing trusted execution mechanisms provide limited support for preserving trust after a localized compromise.}
An application-specific trusted domain protects only the most security-critical logic; the bulk of embedded firmware still runs as a single, monolithic Normal-world RTOS application sharing one privilege level and address space, so one vulnerability can compromise the entire device.
Existing MCU compartmentalization mechanisms~\cite{clements2018aces,kim2018securing,khan2023ec,mera2022d} isolate code, data, and peripherals, but none safely composes this isolation with control-flow protection under interrupts, enforces fine-grained access control over shared data, or provides a remote verifier with evidence to localize and recover from a compromised compartment.
Thus, a third fundamental question is: \emph{\ul{how can an MCU's Normal-world application be fine-grained and interrupt-safe compartmentalized regarding both control and data flow, so that a violation produces evidence letting a remote verifier localize, contain, and selectively recover from it?}}

These limitations share a common root: \textbf{embedded trust is typically treated as a property established at a particular point in time, rather than as a property that must be established, verified, and preserved throughout system execution.}
This project proposes \sys: \textit{\underline{V}erifiable Trust \underline{E}stablishment for Embedded \underline{S}ys\underline{t}ems}, with the objective of developing a continuous trust model for embedded systems.
VEST will investigate how trusted execution environments can be constructed from explicitly selected hardware and software resources and exposed to a remote verifier; how hardware-assisted runtime evidence can efficiently represent control-flow, task, interrupt, and
other security-relevant execution events; and how runtime evidence can be combined with fine-grained isolation to determine the scope of a violation,
contain affected components, and selectively restore and re-attest them.
Rather than treating trusted execution, runtime attestation, and compartmentalization as independent mechanisms, \sys will connect them through a common trust lifecycle in which the verifier can reason about \emph{\ul{what environment was established}}, \emph{\ul{how that environment executed}}, and \emph{\ul{what remains trustworthy following a localized compromise}}.
Thrust~1 spans reconfigurable SoC FPGAs and Cortex-A processors through ARM CCA, while Thrusts~2 and~3 target Cortex-M bare-metal and RTOS software, where the absence of an MMU makes runtime evidence and MPU-based compartmentalization most critical.

Accordingly, the project is driven by three overarching research objectives:

\begin{itemize}
	\item \textbf{\textit{O1}: Establish verifiable application-specific trust.}
	Develop architectures and resource-composition mechanisms that construct
	trusted execution environments according to application requirements and
	enable remote verification of their security-relevant hardware and software
	configuration.
	
	\item \textbf{\textit{O2}: Maintain trust through scalable runtime evidence.}
	Develop efficient runtime measurement and verification techniques for
	bare-metal and RTOS-based embedded systems that capture security-relevant
	execution while bounding measurement and communication overhead.
	
	\item \textbf{\textit{O3}: Preserve trust after localized compromise.}
	Develop evidence-guided compartmentalization, containment, recovery, and
	re-attestation mechanisms that identify affected trusted domains while
	allowing confidence in unaffected components to be retained.
\end{itemize}

Achieving these objectives will move embedded-system security beyond
one-time trust establishment toward a model in which trust can be continuously
reasoned about from system construction, through runtime execution, to
containment and recovery following compromise.

\subsection{Proposed Research}
As illustrated in Figure~\ref{fig:thrusts}, this proposal describes a three-step research agenda, namely \sys: \textit{\underline{V}erifiable Trust \underline{E}stablishment for Embedded \underline{S}ys\underline{t}ems}, driven by the following overarching scientific goal: \textbf{\textit{Design and develop novel compilers, algorithms, and hardware-software methods that configure \ul{verifiable execution domains for trusted applications}, \ul{enable scalable and interrupt-/RTOS-aware remote runtime attack detection for firmware logic}, and \ul{decouple Normal-world software into safe, recoverable compartments}}}.
To this end, \sys first realizes trusted execution domains on programmable FPGA hardware and then leverages ARM CCA's hardware isolation primitives on fixed-silicon Cortex-A systems.
For remote attestation with RTOS support, it leverages TEE hardware, compiler-based instrumentation, and underlying hardware cryptographic engines.
Lastly, \sys achieves compartmentalization of firmware logic through compiler-driven partitioning, analysis techniques, and hardware-assisted enforcement mechanisms.
To achieve this overall goal, we propose the following three research thrusts:

\textbf{Thrust 1: Application-Specific Trusted Execution Domains.}
Conventional embedded TEEs rely on a fixed, platform-defined, monolithic trust boundary rather than one tailored to each application's security and resource requirements, exposing applications to unnecessary shared hardware and privileged components.
This thrust will translate an application's security and resource requirements into an explicit, minimal trusted-domain specification that separates resources across trusted applications, and develop resource-composition algorithms, hardware-assisted isolation, and attestation protocols that expose the resulting domain's configuration to a remote verifier.
We will realize such domains on reconfigurable SoC FPGAs, where dedicated hardware and interconnects are allocated per application, and, through new Root-monitor firmware alone, on Cortex-A processors by using ARM CCA's Granule Protection Tables to decouple the Secure world into least-privilege domains without new hardware.

\textbf{Thrust 2: Scalable Runtime Trust Attestation.}
Control-flow attestation lets a verifier detect control-flow hijacking, but existing evidence and measurement costs grow with program complexity or execution duration and provide limited support for interrupts, asynchronous events, and multitasking.
This thrust will develop scalable runtime attestation for bare-metal and RTOS-based systems, forming evidence around control flow and augmenting it with task transitions, context switches, and interrupt execution.
We will develop evidence-compression and verification algorithms, compiler-based instrumentation, and protected measurement runtimes that bound evidence size by static program and task structure rather than execution duration, enabling efficient remote verification.

\textbf{Thrust 3: Evidence-Guided Trust Containment and Recovery.}
Existing MCU compartmentalization mechanisms impose substantial MPU-reconfiguration overhead, leave correctness under nested interrupts unanalyzed, and leave a data-flow confused-deputy gap a compromised compartment can exploit without violating any control-flow policy.
This thrust will develop real-time- and data-flow-aware compartmentalization with interrupt-safe transitions: compiler-driven partitioning algorithms that jointly reason about MPU region budgets, real-time deadlines, and DMA-capable peripherals, and a fixed-priority transition monitor that routes every cross-compartment transfer through a formally verified exception path rather than ad hoc interrupt masking.
Ambiguity-guided data-flow policies enforce directional MPU permissions where a dependence analysis can resolve the legitimate writer and fall back to hardware-authenticated tags otherwise, while evidence-guided recovery localizes, contains, and selectively restores only the affected compartment.

\textbf{Intellectual Merit.}
This project will advance the system architectures, hardware/software TCB design, and algorithms needed to establish, verify, and preserve trust in embedded systems.
It will develop application-specific trusted execution domains with verifiable resource composition and isolation; scalable runtime attestation for bare-metal and RTOS-based systems; and evidence-guided compartmentalization for localized containment, recovery, and re-attestation. 
Together, these contributions will create a trust lifecycle spanning trusted-environment construction, runtime verification, and post-compromise restoration.

\subsection{Relevance to SaTC}
This project is highly relevant to SaTC as it will strengthen the security of embedded systems, pervasive in industrial automation, transportation, healthcare, and smart infrastructure.
\textbf{Trust} is a verifier's evidence-backed confidence that a device runs the intended software within the intended boundary and stays trustworthy after a localized compromise.
The \textbf{threat} is a remote attacker exploiting memory-corruption or misconfiguration to take over a device, or a compromised Normal- or Secure-world component.
\textbf{Contributions:} hardware-software co-design for verifiable execution, runtime evidence, and compartmentalization with recovery, prototyped on FPGA SoC, ARM CCA, and Cortex-M.
